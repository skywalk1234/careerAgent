## 一、背景与问题

### 1.1 痛点：模型每次都是「从零认识你」

当前对话能力随会话结束而消失。真正想被记住的东西恰恰藏在对话里：**学到哪了、新学了什么技术、项目有什么进展、在追什么岗位、自评卡在哪**。没有它们，规划专家只能给泛泛方向、模拟面试官只能对着简历断言提问。

### 1.2 先厘清：简历是不是就是一种长期记忆？

**是，但只是「结果态记忆」。** 结论先行：**简历与长期记忆不是替代关系，是不同层。**

|     | 简历                 | 长期记忆                      |
| --- | ------------------ | ------------------------- |
| 本质  | **结果态**：你有什么、做过什么  | **过程态 + 时间线**：你怎么一步步走到现在的 |
| 更新  | 稀疏事件（polish / 手动改） | 连续累积（每次对话追加）              |
| 可信度 | 高——用户校验过的事实底座      | 中——需要去噪、防过期召回             |
| 回答  | 「你现在有什么」           | 「你学到现在经历了什么、正卡在哪、想去哪」     |

**简历结构上放不下的东西**（正是长期记忆要接住的）：

| 简历记不了           | 例子                              |
| --------------- | ------------------------------- |
| 进行中的学习进度        | 「Redis 刚学到集群」「正在做 xx 项目」        |
| 自评与短板           | 「Redis 我只会缓存那块，集群不会」            |
| 目标 / 倾向的演化      | 「有点想转 Java」「纠结考研还是工作」           |
| 经历背后的理解深度       | 「QPS 提升 5 倍」≠ 用户讲得清为什么          |
| 被 polish 剪掉的上下文 | 「实习主要做测试，想转开发」——朝 JD 重写时这类话会被丢掉 |

### 1.3 总原则：两路并行、互不覆盖

- **能动简历的只有 polish_resume 和用户手动改**。长期记忆永不写简历、不覆盖简历。
- **简历 = 事实底座**，专家永远以它为准（被用户校验过）；
- **长期记忆 = 过程与时间线**，只存简历装不下、又关乎下一步的信息。

## 二、存储设计：先纠正一个伪二选一

> 问「存原始文本还是存向量库」是个伪命题——**向量只是索引，替代不了原文**。一条向量无法反推出文本，任何记忆系统拼 prompt / 回答用户都还是要原文。真实问题是「**原文放哪、向量放哪、结构化元数据放哪**」三方怎么分。

结论：**原文 + 元数据落表，向量只作为同表上的检索索引**，两者都留。参考的开源项目（SQLite + Qdrant 混合）也是这么做的——Qdrant 的 payload 里带着原文，SQLite 存结构化字段。

### 2.1 借鉴其「检索编排思路」，不照搬其「组件」

| 开源项目                                   | 本方案的取舍                             |
| -------------------------------------- | ---------------------------------- |
| SQLite + Qdrant 双存储                    | ❌ 不引 Qdrant——本项目已跑 pgvector，一处索引即可 |
| **结构化预过滤 → 语义召回 → 综合评分**               | ✅ 核心套路，采纳                          |
| **评分 = (相似度×0.8 + 近因×0.2) × 重要性权重**    | ✅ 采纳，近因加权对学习进度类记忆尤其关键              |
| episode 带 session/timestamp/importance | ✅ 保留为元数据列                          |

## 三、核心设计：单一情景层（事件溯源）

> **关键判断（v0 → v0.1）**：规划专家不仅需要当前状态，更看重**历史状态/演进轨迹**——用户一个月学了 2 项技术、和半年没进展，规划的力度完全不同，这只有时间线能看出来。一个被覆盖更新的「状态行」恰恰丢掉轨迹，还会和情景层形成两套事实。因此**取消状态层**，情景层作为**唯一事实源**（事件溯源思想），「当前状态」只是它按维度投影的结果，读取时现算，**不另存一份真相**。

### 3.1 情景表：唯一存储

```
user_episodic_memory（追加式，事件即真相）
  id           PK
  user_id          -- 硬隔离，绝不可少（记忆是敏感数据）
  session_id       -- 结构化过滤维度
  category         -- 维度：learning_progress / project / goal / self_assessment / ...
  content          -- episode 原文（唯一事实来源，喂 prompt 用）
  importance       -- 抽取时模型打分 0~1
  superseded_by_id -- 可空：非空=本条已被哪条新 episode 取代（current-view 活跃行 = IS NULL）
  created_at       -- 近因加权 / 投影排序
  embedding VECTOR(1536)  -- DashScope text-embedding-v1，复用现有嵌入管线
```

**为什么不需要单独的状态表**：任何「当前状态」都能由这张表**读取时投影**出来，见 §3.2 两种视图。少一张表 = 少一份会漂移、会与情景打架的真相。

### 3.2 读取投影：三种视图，按需现算

> ⚠️ 修正：**「时间最新的一条 = 当前状态」只对单一维度成立**。用户的当前状态是**按维度聚合**的——Redis 的进度、项目进展、目标最新说法、自评短板各有各的「最新」，不是全局最新那一条。
> 
> 三个检索轴各司其职：**category 轴**（元数据）按记忆*类型*分组，**时间轴**按*新近/窗口*分组，**主题轴**（向量）按*说的是同一件事*分组。三类视图分别用不同的轴组合。

```
视图 A：current-view（当前状态投影，喂主对话开场 / 规划专家）
   取「未被取代的、每个 category 时间最新」的若干条
   → 需要干净汇总时，可再让轻量 LLM 折叠成一段「当前画像」
   SQL 思路：NOT superseded + GROUP BY category 取 max(created_at)（或直接 category + 时间倒序 top-k）
   用轴：category + 时间（不做向量）

视图 B：timeline-view（近期轨迹，喂规划专家做「怎么走到今天」）
   按 category / 时间范围取最近 N 条，保留演进顺序
   → 规划专家读它判断「进步速度、卡点演变、目标漂移」
   用轴：category / 时间窗

视图 C：thread-trace（主题线程轨迹，串「同一个主题跨时间的完整演进」）
   embed 主题描述 → 语义 top-k → 按 created_at 排序
   → 解决：同一项目/同一技能的学习进展散落在不同时间点、中间夹着无关主题，
     只有语义能把它们从时间线上「拎」出来串成一条线
   → 向量决定「哪些 episode 属于这条线」，时间决定「这条线怎么展开」
   用轴：主题（向量）+ 时间排序
```

- current-view / timeline-view 按 category + 时间过滤即可，量小、要的就是最新，**不需要向量**；
- **向量检索只出现在两处**：跨维度语义回忆（「用户提过哪些和存储/数据库相关的点」）与**视图 C 主题成线**——前者是广撒网，后者是收拢一条线；
- ⚠️ 视图 C 是模糊召回：可能捞进相似但不同的主题，也可能漏掉措辞差异太大的同主题旧话（召回不全）。定位是「召回助手」而非「保证全集」；进阶可在写入时给 episode 打主题标签做精确索引、向量退居兜底（v0 不做）。

### 3.3 去重 / 防漂移：supersede，而不是删

纯情景层会踩的坑：**语义召回会把过期事实翻出来**。第 1 周「Redis 集群还没学」、第 4 周「集群学完了」都在库里，向量检索可能把旧的也捞出来，越往后漂移越重（这正是状态层原本防的，现在由情景层自己防）。

对策：抽取时若新 episode **取代了同维度同事实的旧进展**，在**旧行**填 `superseded_by_id`（指向取代它的新行，逻辑标废，不物理删）。效果：

- current-view / 语义召回默认**跳过被取代行**，不翻旧账；
- 完整历史仍在（chat_history 永远保留原文，被取代的旧行也在，timeline-view 可查），信息不丢；
- 若嫌 supersede 复杂，退路是**加强近因权重**（把评分里 recency 提到主导），接受旧行偶发混入。

**关于 scale 的实话**：单用户记忆撑死几百条，关键词 + 元数据过滤已很快很准。向量真正的增量价值是跨关键词语义召回；元数据过滤 + 近因排序才是日常命中大头。

### 3.4 与现有存储的分工

| 存储                   | 承载      | 角色                            |
| -------------------- | ------- | ----------------------------- |
| MySQL `chat_history` | 每轮会话/消息 | 原始对话的**源头事实**（不动它，记忆由此抽取、可回溯） |
| pgvector（新表）         | 情景记忆    | 记忆层本体（建议独立 schema，勿与岗位表混放）    |

## 四、抽取与写入时机

```
对话进行（chat_history 照常记录）
   ↓ 会话结束 / 或检测到关键信息后
抽取 LLM：读本次会话 + 近端已有 episodes → 输出
   ├─ 新增 episodes：{content, category, importance, superseded_by_id?} 若干条
   └─ 合并判断：若与同维度近期 episode 是「同一事实的新进展」→ 在旧行填 superseded_by_id 指向新行，逻辑标废
        → 追加进 user_episodic_memory
```

要点：

- **抽取是异步、低配 LLM 的**（对会话做一次性结构化摘要），不占用主对话时延；
- **先落 chat_history，再抽记忆**，保证原始事实永远可回溯；
- 只抽状态相关的信号，**不是每句都沉淀**——控制噪音与体积；
- 不做持久化的状态层，也就没有「状态合并」这一道双写。
- **抽取口径：用户陈述是唯一事实源，助手回答只是上下文**。抽取 LLM 必须读完整对话（两侧）——很多用户句单独不可解（「对，就是那块」「好，就按你说的来」要助手前一轮才能定位指代）；但写入的 episode **必须能溯源到「用户说过 / 确认过 / 应允过」**。模型单方建议、用户从未回应的，不存或降级（标 user_acknowledged=false）；用户**应允的下一步**（模型提议、用户认可）可存为 `goal`。
- **对话连续性（助手上次建议到哪）不进情景层**：那不属于用户画像，chat_history 已全文留存，需要时直接检索原文，勿重复提炼。

## 五、读取与消费

| 消费方        | 读什么                              | 用途                                |
| ---------- | -------------------------------- | --------------------------------- |
| 主对话        | current-view（每会话开场）              | 让助手始终带着「用户现在学到哪」回话                |
| 主对话        | timeline-view / 向量语义召回           | 接住「上次你说在做 xx，进展如何」「我提过哪些和 xx 相关的」 |
| 职业规划专家（未来） | current-view + **timeline-view** | 从「现在坐标 + 进步速度 + 卡点演变」生成未来方向与规划    |
| 模拟面试专家（未来） | 简历（事实底座）+ current-view 的短板/深度    | 追问素材 + 面试报告                       |

## 六、风险与取舍

| 风险                       | 对策                                                              |
| ------------------------ | --------------------------------------------------------------- |
| 抽取幻觉——记忆沉淀了对话中没说过的事      | 从 chat_history 抽取时约束「只转述用户明确信息」；保留源 session 可回溯                 |
| 过期事实被语义召回翻出（漂移）          | supersede 标废 + current-view/召回默认跳过被取代行；退路为加强近因权重                |
| 「当前状态」无存储、每次现算           | current-view 是 SQL 级投影（category + 时间过滤），成本极低；只在要干净画像时才轻量 LLM 折叠 |
| 记忆与简历冲突（记忆说会 Kafka、简历没有） | **以简历为事实底座**，记忆只作「在学/自评」侧写，不冒充简历事实                              |
| 噪音堆积                     | 只抽状态信号、importance 打分；supersede 收敛同维度重复                          |
| 敏感数据                     | user_id 硬隔离、独立 schema；必要时按用户可清空                                 |

## 七、决策记录与待定问题

**已定（随 M1/M2 落地）**：

1. supersede：**保留**（`superseded_by_id` 列 + 部分索引），不做「近因强加权」退路。
2. 存储位置：复用 pgvector 现有实例、同 public schema，真实隔离靠 `user_id` 列（代码读写即按此）。
3. 抽取触发粒度：**每轮助手回复落库后后台触发 + 滑动窗口**（非会话结束，本架构无会话结束事件）。

**仍开放**：

1. `importance` / 近因权重、`memory_recall_threshold` 等参数标定——待真实对话数据调。
2. current-view「每类一条」的上限是否要放宽为「每类各取 N 条」——当前取舍见 §3.2。
3. 进阶：写入时给 episode 打主题标签做精确索引、向量退居兜底（thread-trace 召回不全问题的终极解法，暂缓）。
4. 长会话历史增长：`build_llm_messages` 每轮全量重放会话，超长会话需「窗口 + 旧文摘要」（非记忆层，属 chat 上下文治理）。
