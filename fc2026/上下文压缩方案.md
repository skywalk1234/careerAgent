# 会话上下文自动压缩方案

> 目标：主对话（`ai-service-py`，DeepSeek）在**不拉长 SSE** 的前提下，把不断增长的会话上下文自动折叠成摘要，模拟 Claude Code 的「上下文太长就自动压缩」体验。
>
> 决策（2026-09-07 与用户确认）：
> 1. 压缩动作在**后台异步**执行（每轮回复结束后 fire-and-forget，下一轮生效）；
> 2. 触发信号**只用 API 每次返回的真实 `prompt_tokens`**（不用本地估算）。
>
> 对应代码：`fc2026/ai-service-py/app/routers/chat.py`、`app/services/chat_service.py`、`app/services/llm.py`、`app/models.py`、`app/config.py`

---

## 一、现状与问题

[chat_service.build_llm_messages](fc2026/ai-service-py/app/services/chat_service.py#L92) 构造发给 DeepSeek 的上下文时：

```python
for m in history:
    if m.role in ("user", "assistant"):
        messages.append({"role": m.role, "content": m.content})
```

`history` 来自 [chat_service.list_messages](fc2026/ai-service-py/app/services/chat_service.py#L58) —— **该会话 MySQL `messages` 表全量、按时间升序、不做任何截断**。也就是说：

- 会话越长，每次请求的 prompt 线性增长，成本与首 token 延迟都变大；
- 大概率触达模型上下文上限时，早期对话被挤掉，能力反而下降。

## 二、关键概念澄清：为什么不是「累加输入 token」

最初设想是「每次调用模型拿到当前输入 token，**累加**，到阈值压缩」。这里有一个语义差异需要澄清：

- 每次发给 DeepSeek 的 prompt 都**包含整段历史**（`build_llm_messages` 全量拼），所以每次调用的 `prompt_tokens` ≈ 当前上下文大小，**不是单调递增的增量**；
- 真正该监控的是「**当前这一条 prompt 有多大**」，达到阈值就把最老的一段对话折叠成摘要，让下一条 prompt 变小。

因此本方案的口径定为：**每轮取 API 返回的真实 `prompt_tokens`（当前上下文规模）做阈值判断**，而不是把历次值累加。这与 Claude Code 的体验一致——它也是在上下文接近上限时把最早的消息滚成摘要。

## 三、总体设计

```
第 N 轮对话
  └─ stream 结束 → 落库 assistant 消息
       ├─ 后台：长期记忆抽取（现有，memory.py）
       └─ 后台：上下文压缩（新增，context_compress.py）   ← 新增
            ├─ 读本次 API prompt_tokens（来自本轮最后一次模型调用）
            ├─ ≥ CONTEXT_COMPRESS_THRESHOLD ？
            │    └─ 是：把最老的若干轮对话（保留最近 N 条原文）
            │        合并进滚动摘要，写回 sessions.context_summary
            │        并推进 sessions.compressed_count
第 N+1 轮（对话前，纯内存）
  └─ build_llm_messages 组装上下文：
        system = 基础角色
               +【历史对话摘要】(已压缩较早轮次)
               +【历史工具执行】(见 §八：从剩余原文各条 assistant 消息的 agent_trace
                  抽 tool 步骤，按 toolName 去重，同一工具只留最近一次完整 result)
               +【长期记忆】
        history = messages[compressed_count:]   ← 折叠过的旧消息不再进 prompt
```

### 关键性质

1. **异步、不阻塞**：压缩在 SSE 收尾后由 `asyncio.create_task` 触发，与现有长期记忆抽取（[chat.py 的 `_spawn_memory_extraction`](fc2026/ai-service-py/app/routers/chat.py#L35)）同款模式。代价是「跨过阈值那一轮」的 prompt 仍偏大一次（过冲一轮），随后自动回落。
2. **持久化**：摘要与折叠边界落在 `sessions` 表，重启/多请求不重复压缩，也不产生状态丢失。
3. **保留最近原文**：最后 N 条消息始终以原文保留（模型对近期对话有精确记忆，摘要只覆盖较早轮次）。当前问题本身当然永远在上下文里。
4. **与长期记忆互补**：长期记忆（pgvector）是「跨会话的用户事实沉淀」；上下文压缩是「本会话早期轮次的精炼」。两者都作为 system 分区的背景注入，互不覆盖。
5. **对话前 tool 去重与后台折叠互补**：后台折叠（§四）是「回复结束后、异步、把最老轮次折叠进摘要」；tool 去重（§八）是「下一轮组装上下文前、同步、对仍保留原文区间的历史工具执行做按名去重」，只影响送进模型的上下文，不写 DB。

## 四、判定口径与触发

### 4.1 拿到真实 prompt_tokens

| 调用形态 | 出现时机 | 拿 usage 的方式 |
|---|---|---|
| 工具循环 `llm_with_tools.ainvoke(messages)`（非流式） | 每轮**可能**出现 | 响应自带 `usage`，langchain 映射到 `AIMessage.usage_metadata.input_tokens` |
| 最终回答 `get_llm().astream(messages)`（流式） | **每轮必有** | 需开启 `stream_options={"include_usage": true}`，末尾带 usage 的 chunk 内容为空串、携带 `usage_metadata` |

因此需要给 [llm.py 的 `get_llm()`](fc2026/ai-service-py/app/services/llm.py#L27) 增加 `stream_usage=True`，DeepSeek 官方文档确认支持 `stream_options.include_usage`（流式响应末尾含 `usage: {prompt_tokens, completion_tokens, total_tokens}`）。现有消费方（chat.py、interview.py）对空 content chunk 都已 `if not text: continue`，不受影响。

### 4.2 触发条件

本轮最后一次模型调用返回的 `prompt_tokens ≥ CONTEXT_COMPRESS_THRESHOLD` 时，后台执行一次压缩。

### 4.3 折叠边界（fold boundary）

`history`（messages 全量，时间升序）长度为 `L`，会话已折叠 `compressed_count` 条：

```
candidate = L - CONTEXT_COMPRESS_KEEP_RECENT   # 保留最近 N 条原文
boundary  = max(compressed_count, candidate)    # 只前移、不倒退
if boundary - compressed_count < CONTEXT_COMPRESS_MIN_NEW:
    不压缩（新增条数太少，避免频繁小步压缩）
```

折叠对象 = `history[compressed_count : boundary]`，合并进已有摘要后：

```
context_summary  := summarize(existing_summary, history[compressed_count : boundary])
compressed_count := boundary
```

### 4.4 每次压缩后 prompt 规模估算（仅日志）

压缩后下一条 prompt 的规模大致 = 摘要 token + 最近 N 条原文 + 长期记忆 + system。不做精确本地估算，靠下轮 API 返回的 `prompt_tokens` 自然回落来验证。

ORM 侧 [models.ChatSession](fc2026/ai-service-py/app/models.py#L15) 增加：

| 列 | 类型 | 含义 |
|---|---|---|
| `context_summary` | `MEDIUMTEXT NULL` | 已折叠的最早一段对话的滚动摘要（纯文本，中文） |
| `compressed_count` | `INT NOT NULL DEFAULT 0` | 已折叠进摘要的旧消息条数（messages 时间升序前缀下标） |

## 六、摘要生成

### 6.1 摘要 LLM

新增专用工厂 `get_summary_llm()`（对齐 `get_json_llm` 风格）：

- 显式关闭 thinking（`{"thinking":{"type":"disabled"}}`）——摘要任务求快求稳，隐藏推理徒增延迟与 token；
- 低温度（0.2）+ 适中 `max_tokens`（2048）+ 较长 timeout（150s），单次压缩调用控制在一次往返内。

### 6.2 摘要 prompt（中文）

```
你是「对话摘要器」，服务于大学生求职规划助手。你需要把一段较早的对话合并进会话摘要，供后续轮次作背景参考。

【输入】
- 【已有摘要】：之前折叠轮次的摘要（可能为空，表示首次压缩）
- 【本轮待折叠对话】：按时间顺序的 user / assistant 消息原文

【规则】
1. 输出是对已有摘要 + 待折叠对话的合并结果，必须自包含、无悬空指代；
2. 优先保留：用户的目标/决定/承诺、项目与学习进展、技术栈与掌握程度、已给出并应长期参考的关键结论；
3. 助手早期的寒暄、过程性输出、重复解释可删除；保留每件事的「状态与时间感」（刚开始/已学完/正在做）；
4. 以精简的要点式中文输出，长度控制在几百 token 内，不逐条复述；
5. 不要输出 JSON，只输出压缩后的摘要文本。
```

## 八、对话前：历史工具执行去重压缩（新增）

> 目标：每轮工具执行的**完整 result** 已随 assistant 消息落库到 `messages.agent_trace`（见 `save_assistant_message` 的 `agent_trace` 参数）。若把这些历史工具执行原样注入后续上下文，同一工具（如 `recommend_specific_jobs` / `recall_memory`）在长会话里会被反复调用、每次结果可能数 KB，上下文随调用次数线性膨胀。故在**每轮组装上下文前**先按 toolName 去重一次。

### 8.1 触发时机与位置

- 时机：**对话前**——用户新消息到达、`stream_message` 调 `build_llm_messages` 组装上下文那一刻；与 §四 的后台折叠压缩（回复结束后、异步、折叠最老轮次）是互补的两条链路。
- 位置：`build_llm_messages`（`app/services/chat_service.py`）内部。**纯内存、不落库**——DB 仍留档每次完整 result，只替换送进 prompt 的副本（对账/审计不受影响）。

### 8.2 去重规则

遍历 `history = messages[compressed_count:]`（时间升序，含每条 assistant 消息的 `agent_trace`）：

1. 从每条 assistant 消息 `agent_trace.steps` 中取 `type == "tool"` 的步骤，得 `(toolName, toolParams, outputSummary, result)`，按时间顺序排列；
2. 同一 `toolName` 出现多次时，**最近一次保留完整 `result`**；
3. 更早的同名步骤**不删除**，但其 `result` 整体替换为占位文本 `Old tool result content cleared`（保留 toolName/params 与时间次序，只清返回内容）。

占位文本的语义是告诉模型「该工具此前确实执行过、只是旧返回已被清理」，避免它误判成从未调用。若想进一步省 token，占位行可只保留 toolName、不重复参数与 outputSummary。

### 8.3 注入形式：system 文本分区（不回放 role=tool 消息）

历史 assistant 消息落库时已被折叠成纯文本最终回答，工具调用过程只留在 `agent_trace`，**不能**把旧工具执行回放成 `role: "tool"` 消息——OpenAI/DeepSeek 要求 tool 消息必须紧跟声明了对应 `tool_call_id` 的 assistant 消息，回放会破坏该约束、直接 API 报错。因此沿用【长期记忆】【历史对话摘要】的做法，以 **system 背景分区**注入，并标注以工具/用户提供的真实数据为准：

```
以下是你此前在本会话中调用工具执行过的记录（同一工具只保留最近一次的真实返回，更早返回已清理；
仅作背景参考，事实以本次工具调用返回或用户提供为准）：
- recommend_specific_jobs（最近）→ 返回：{…最新完整 result…}
- recommend_specific_jobs（更早）→ 返回：Old tool result content cleared
- get_student_profile（最近）→ 返回：{…}
```

分区在 system 中的顺序：基础角色 →【历史对话摘要】→【历史工具执行】→【长期记忆】。

### 8.4 规模控制

- 去重后真正进上下文的有效结果 ≈ **不同 toolName 种数 × 各自最近一次 result 大小**，不再随调用次数线性增长；重复项每行只剩占位文本。
- 受 `compressed_count` 约束：被 §四 折叠进摘要的最老轮次已不在 `history`，其工具执行自然不进本分区——折叠越深，本分区越小，两套压缩协同收敛。

### 8.5 代码改动点（延续 §七 口径，尚未实现）

- `app/services/chat_service.py`：新增纯函数 `build_tool_history_block(history: list[ChatMessage]) -> str | None`——按 8.2 抽 agent_trace tool 步骤、按 toolName 去重、拼 8.3 文本块；无可注入步骤时返回 `None`。
- `build_llm_messages`：拿到该块后在 system 按 8.3 顺序插入。
- `app/config.py`：`context_tool_history_enabled: bool = True`（总开关，关闭则跳过本分区；与后台压缩开关独立）。
- 不改 models、不加 DDL：数据源即已有的 `messages.agent_trace`（旧消息为空 dict → 自然跳过）。

### 8.6 与后台折叠压缩的关系

| 维度 | §四~§七 后台折叠压缩 | 本 §（对话前 tool 去重） |
|---|---|---|
| 触发 | 每轮回复结束后、后台异步 | 下一轮组装上下文前、同步 |
| 处理对象 | 最老的若干轮 user/assistant 文本 → 滚动摘要 | 仍在原文区间内的历史工具执行 → 按名去重 |
| 落地 | 写 `sessions.context_summary / compressed_count` | 不落库，仅替换送 prompt 的副本 |
| 是否写 DB | 是 | 否 |

## 九、时序举例

会话 messages（时间升序）共 10 条 = 5 轮。阈值 30k、keep_recent=8、min_new=2。

1. **第 6 轮**：prompt 含 1~10 条 + system，API 返回 `prompt_tokens = 31k ≥ 30k` → 触发后台压缩；
2. 后台算 `L=12`（第 6 轮 assistant 已落库）、`compressed_count=0`：
   - `candidate = 12 - 8 = 4`，`boundary = 4`，`4 - 0 ≥ min_new` 成立；
   - 摘要 = `summarize(无, messages[0:4])`（第 1、2 轮 user/assistant 两条一问一答）；
   - 回写 `context_summary`、`compressed_count = 4`；
3. **第 7 轮** `build_llm_messages`：
   - system 注入【历史对话摘要】= 第 1~2 轮摘要；
   - 对话部分只带 `messages[4:]` = 第 3~6 轮原文（8 条）+ 当前问题；
   - prompt 规模回落到 ~摘要 + 8 条原文，明显小于阈值；
4. 会话继续到第 9 轮再次 `prompt_tokens ≥ 30k` → 折叠 `messages[4:boundary']`，`compressed_count` 前移，摘要滚动累加。

## 十、风险与取舍

| 风险 / 取舍 | 说明 | 对策 |
|---|---|---|
| 过冲一轮 | 触发的那个请求 prompt 已偏大（API-only 口径的固有滞后） | 用户已接受（后台异步方案）；阈值设富余即可 |
| 摘要信息丢失 | 折叠=有损压缩，早期细节可能被合并 | 保留最近 N 条原文；摘要 prompt 强制保留目标/进展/决定 |
| 后台竞态 | 连续两轮快速触发、或压缩进行中新轮已开始 | 模块级 session 重入锁；压缩只前移边界、幂等 |
| `stream_options` 兼容 | 部分 OpenAI 兼容网关不支持 | DeepSeek 官方确认支持；`_extract_prompt_tokens` 拿不到就跳过本轮（不阻塞） |
| 多调用方影响 | `get_llm()` 加了 stream_usage | chat.py/interview.py 均已 `if not text: continue`，末尾 usage chunk 内容为空，无副作用 |
| DDL 未执行 | ORM 查询 `sessions` 会因缺列报错 | 部署前必须执行附录 A 的 ALTER |
| 回放 `role=tool` 的结构约束 | OpenAI/DeepSeek 要求 tool 消息紧跟对应 assistant(tool_calls) | 不回放 tool 消息，改以 system 文本分区注入（§8.3） |
| 工具执行分区挤占上下文 | 即使去重，每工具最近一次 result 仍占一定 token | 随折叠变深分区自动变小（§8.4）；`context_tool_history_enabled` 可整体关闭 |
| 占位文本被误读为真实返回 | 模型可能把 `Old tool result content cleared` 当成结果内容 | 分区前缀与占位行都明确标注「更早返回已清理」，且分区声明以工具真实数据为准 |

## 十一、验证

1. 手动执行附录 A DDL；
2. 启动 ai-service，跑一个长会话（或临时把 `context_compress_threshold` 调小，如 500）快速验证：
   - 触发轮的日志出现「上下文压缩：折叠 X 条… 摘要 token …」；
   - 下轮 `sessions.context_summary` 非空、`compressed_count > 0`；
   - 后端日志中下轮 API `prompt_tokens` 显著回落；
3. 纯聊天（无工具）与工具调用混合两条链路都要过一遍，确认均能拿到 usage 并触发；
4. 对话前 tool 去重（§八）：构造一个会多次调用同一工具（如两轮都要 `recommend_specific_jobs`）的会话，重开历史后检查组装出的【历史工具执行】分区——同一 toolName 只有最近一次带完整 result，更早行是 `Old tool result content cleared`；纯聊天会话该分区为 `None`；DB 里每次完整 result 仍保留。

## 附录 A：手动 DDL

```sql
-- MySQL chat_history 库，chat_history.sessions 表
ALTER TABLE sessions
    ADD COLUMN context_summary MEDIUMTEXT NULL COMMENT '已折叠的最早一段对话的滚动摘要（上下文压缩）',
    ADD COLUMN compressed_count INT NOT NULL DEFAULT 0 COMMENT '已折叠进摘要的旧消息条数（messages 时间升序前缀）';
```
